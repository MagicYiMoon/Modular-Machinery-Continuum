# 服务器机器定义与控制器注册同步

以下同步改进包含在 MMC 2.0.0 中，网络协议为 49。请同时更新客户端与服务端；旧 1.4.4 JAR 使用协议 35。

## 机器内容以服务端为准

进入服务器后，机器结构、配方、显示名称、颜色、蓝图要求等运行数据由服务端发送。GUI 保存写入服务端机器文件，完成重载后向在线客户端同步。客户端本地机器 JSON 不参与该服务器的运行，也不会被服务器文件覆盖。

使用 `register` 创建的机器完成加载后，可以在 GUI 中编辑，并先使用通用控制器。独立控制器是 Forge 方块注册项，新方块仍需服务端重新启动后才能生成。

## 缺少独立控制器时自动取得注册信息

Forge 在玩家进入世界前检查方块与物品注册表。机器文件中的新 ID、首次开启的独立工厂控制器，或服务端保留的历史控制器，可能没有在客户端启动时注册。相同 JAR 也可能因此进服失败。

改进后的流程：

1. 服务端在 Forge 注册表同步之前发送已注册的机器控制器身份，包括普通／工厂控制器。
2. 客户端将身份写入 `config/modularmachinery/server-controller-cache.json`。
3. 本次运行已具备全部所需 ID 时，正常继续连接；结构与配方 JSON 无需相同。
4. 缺少 ID 时，提示“已自动缓存，请完全退出并重启客户端”。重启时先读取缓存并注册对应方块，再次连接即可。

此步骤不要求手动复制机器目录或修改 `controller-registry.json`。不同服务器与本地机器的注册项以并集保留，服务器删除定义也不会自动删除历史 ID。只有名称、颜色、配方、蓝图要求等内容变动时，不需要因为这些内容差异重启客户端。

单人／局域网房主的内置服务器与客户端共用注册表，跳过登录前缓存交换。

## 文件与兼容边界

- 缓存只记录本模组控制器的机器 ID 和是否存在工厂控制器，不下载脚本或覆盖作者机器文件。
- 本地 `controller-registry.json` 继续保存本地机器的历史身份；服务器取得的身份单独保存在缓存中。
- 客户端与服务端仍需使用兼容的模组版本和可选依赖。此机制不修复其他模组的缺失注册项。
- 两个不同机器若派生出相同方块 ID，例如 `foo` 的工厂控制器与 `foo_factory` 的普通控制器，缓存会拒绝冲突并保留原文件。请为冲突的整合包使用不同实例或调整机器 ID。
- 缓存损坏、权限不足或写入失败会明确断开并记录原因，避免继续显示模糊的注册表缺失提示。

Forge 的方块注册表在启动时冻结，因此新增独立方块仍有启动要求。该改进自动准备客户端下次启动所需的注册信息；它不在连接过程中动态增加真实方块。
