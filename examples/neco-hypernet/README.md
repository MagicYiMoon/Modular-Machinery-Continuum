# HyperNet 模块、连接卡与配方示例（MMC 2.0.0）

本目录演示机器配置、物理模块、连接卡、配方算力消费和处理器被动散热。主动冷却和电路维修已接入；只读网络监控、TOP 与 GUI 编辑入口已接入，研究数据库、研究站与独立终端已接入，研究定义与配方门槛可视化已接入；本例不采用新星工程的机器或平衡数值。

需要 MMC 2.0.0、Forge 1.20.1、Java 17；示例脚本另外需要 CraftTweaker 14。AE2 不是该后端的依赖。基础算力演示先将 `hn_sample_center.json`、`hn_sample_processor.json`、`hn_sample_node.json` 三份机器定义放到 `config/modularmachinery/machinery/`，将 `hn_computation_recipe.json` 放到 `config/modularmachinery/recipes/`，将 `hypernet_modules.zs` 放到 `scripts/`。数据库、研究站和终端按本文对应章节另行配置。启动或按现有定义／脚本重载流程载入。独立控制器的注册限制仍按现有同步文档处理。

中心与处理器使用工厂控制器，消费者使用普通控制器。本例不需要蓝图。相对控制器坐标均为世界竖直方向：

| 机器 | Y=-1 | Y=+1 | Y=+2 | Y=+3 | Y=+4 | Y=+5 |
| --- | --- | --- | --- | --- | --- | --- |
| `hn_sample_center` | FE 输入舱 | 石头 | 物品输入总线 | 物品输出总线 | 空 | 空 |
| `hn_sample_processor` | FE 输入舱 | 铁块 | 升级总线 | 铁块 | 物品输入总线 | 物品输出总线 |
| `hn_sample_node` | FE 输入舱 | 金块 | 物品输入总线 | 物品输出总线 | 空 | 空 |

升级总线与物品输入总线之间留有一块铁块，防止输入总线的自动取料抽走模块。旧处理器示例的输入／输出总线分别在 Y=+3／+4；更新本示例后需按新位置搭建，已有自定义机器不自动改动。

使结构成型并为中心和处理器供电。脚本为它们各增加一条具名核心线程和 1 FE/t 工作配方；处理器还需要升级总线中同时有 CPU／GPU 与 RAM。其它维修、冷却线程不受模块门槛阻挡。

脚本将钻石映射为 CPU、绿宝石映射为 GPU、红石映射为 RAM。CPU 最多累计两件、GPU 一件、RAM 两件；此上限按整台机器合并静态升级类型计算。硬件属性来自机器 `hypernet.modules`，不是物品 NBT；`upgrade` 填升级类型名。`capacity` 是每件算力／RAM 上限，`energy` 是每件满载的 FE/t，必须是非负整数。CPU 和 GPU 共用一种算力。

两颗 CPU、一颗 GPU、两件 RAM 时，算力为 `min(2×2+3, 2×4)=7/t`；满载模块耗能为 91 FE/t，另有核心配方费用。RAM 按实际使用的 7 容量收费。模块依总线中顺序分配负载，每件模块累计耗能向上取整，同 tick 多次小额请求不会反复收取同一份取整费用。

中心使用内置 HyperNet 网络密钥卡（`modularmachinery:hypernet_connect_card`，堆叠上限 1，可从创造物品栏取得）。手持卡片右键成型中心写卡，再右键成型处理器／消费者连接。卡会显示维度和世界坐标；目标中心需处于已加载、可进行方块 tick 的区块中。写卡时中心核心可停机，建立连接时中心核心必须运行。当前要求操作者具有机器与网络归属权限，不能用分享卡绕过权限。

模块负载目前只使用机器真正绑定的 MMC 普通 FE 输入舱；可由外部电源给这些舱充电。ME／EU／组件代理等其他能源后端未接入此原子扣费路径。模块消费同时受当前储能和原生舱实际传输上限约束，多次请求不能绕过本后端的每 tick 限额。模拟和失败请求不扣 FE。模块变动后本 tick 剩余供给撤销，最早下一 tick 重建；算力不跨 tick 存储，断线、换中心或重载不能补领。

完整阶段状态见 [算力适配记录](../../docs/NECO_GUIDE_ZH.md)。

## 配方算力需求

连接消费者并供电后，输入沙子可运行 JSON 示例，输入圆石／泥土可运行 CT 示例。算力在每个实际推进进度的 tick 消费，完成后等待输出空间不再收费。需求是网络资源，不对应某个舱室。

```json
{"type":"modularmachinery:computation","io-type":"input","amount":2.0,"triggerFailure":false}
```

`amount` 是每份配方每 tick 的有限非负算力。只支持输入；零需求仍要求有效消费者连接。多条算力需求相加检查，启动时按可用算力限制实际批量；运行中需求按已确定的批量计算，不会因短缺自动缩小正在运行的配方。单条需求可用 `parallelizeUnaffected: true` 免除批量倍增。修改器目标为 `modularmachinery:computation`，可加减或乘算需求值。

CT 方法为 `.requireComputationPoint(2.0)` 或 `.requireComputationPoint(2.0, true)`。默认 `triggerFailure=false`：算力不足或连接不可用时保留进度暂停，即使机器设置 RESET／DECREASE、配方开启失败取消，也不会因此丢弃投入。显式 `true` 才使用现有失败动作和配方取消策略。多条需求任意一条启用此开关时，合并请求失败按失败策略处理。

源版在没有绑定中心时会直接销毁运行配方，本移植对此采用保留进度暂停，避免操作连接卡时丢失投入；缺后端也明确阻止启动，不能绕过算力。持续需求登记已接入，监控区分需求、实际交付与当时供给。默认按实际工作逐 tick 竞争共享预算；中心可开启后文的公平调度。无论哪种策略，都不预留未来 tick 容量。

算力需求不支持 selector、延迟触发、重复触发或忽略输出检查；填写这些非默认值会拒绝载入。算力及处理器模块 FE 的整笔请求不足不扣款；消费者其它每 tick 资源先模拟检查，再提交算力和其它 IO。第三方组件若模拟成功而实际提交失败，不能保证全配方跨组件回滚。

## 处理器热量

示例处理器启用了以下配置。已有机器没有 `thermal` 时不启用热量；配置只能放在处理器角色中。

```json
"thermal": {"overheat-threshold": 1000, "heat-distribution": 4}
```

每实际供给 1 点算力产生 2 HU，分数值累加；模拟、失败和空闲不发热。`overheat-threshold` 是正整数过热阈值，`heat-distribution` 是非负整数基础散热量。被动散热不另外耗 FE，离线或区块卸载期间不补算散热。填 0 会关闭被动散热，启用前应提供下节的主动冷却配方，以免机器永久过热。

温度不超过阈值的 25% 时，每 tick 散去基础量的 25%；25%～75% 时乘以 `0.25 + 热量比例`；超过 75% 时乘以 1。可选 `dynamic-pattern` 填现有动态结构名，使用实际测得的扩展段数放大散热，最低按 1 段计算。保留小数散热，避免基础量较小时整数截断导致永远不能冷却。

热量达到 85% 后，供给效率按 `(1 - 热量比例) / 0.15` 降低；模块需为降效前的计算工作付 FE。例如效率为 2/3，实际供给 1 点需要承担 1.5 点模块负载。效率在本 tick 第一次计算硬件时采样，同 tick 内拆分请求不会改变取整或效率规则；后续请求触发过热时仍立即停止供给。

达到过热阈值后，指定计算核心停机，其它线程可继续工作。过热状态会保持到热量降为零，被动散热此时按完整基础量计算。热量和过热状态保存在控制器私有数据中，重载、换运行实例和世界保存／加载不会将其当作瞬时算力预算清空；客户端方块更新不公开这些私有数据。拆掉控制器后重新放置是否保留其所有私有状态仍按控制器现有掉落规则处理，这不是散热操作。


## 主动冷却与中心电路维修

处理器的 `thermal` 和中心的 `circuit` 都是可选配置。旧定义没有这些字段时，不新增相应限制。中心示例加入：

```json
"circuit": {"capacity": 10000, "min-wear": 1, "max-wear": 3, "wear-chance": 0.1}
```

`capacity` 为正整数；初次启用时满耐久。核心每工作到世界 tick 的 20 倍数时检查一次磨损，停止和等待输出不磨损，离线不补算。概率为 `min(1, max(0.01, wear-chance × (连接数/连接上限 + 有效供给容量/承载上限)))`。容量来自在线处理器硬件和降效结果，按中心承载封顶，不是实际已消费量；查询不扣 FE、不发热。`wear-chance` 必须在 0～1，0 仍保留源版 1% 概率下限；要关闭磨损可令 `min-wear=max-wear=0`。磨损在 `[min-wear,max-wear)` 取整数，两者相等时取该固定值，最低耐久为零。低于容量 5% 时核心停止、网络不可用，独立维修线程仍能运行。

配方增加以下输入需求，另配普通物品／流体投入、产物和 FE/t 即可：

```json
{"type":"modularmachinery:hypernet_cooling","io-type":"input","amount":20}
{"type":"modularmachinery:hypernet_circuit_repair","io-type":"input","amount":100}
```

两种 `amount` 均为非负整数，表示每份配方**成功完成时**移除的 HU 或修复的耐久。启动要求本机已成型且配置了对应系统；冷却只用于处理器，维修只用于中心。多条同类需求合并检查、按实际批量累加，`parallelizeUnaffected: true` 按一份计；冷却还受 `thermal.dynamic-pattern` 的实测段数限制（缺失／零段按 1）。维修启动不能超过缺损量，冷却启动不能超过现有热量。材料照常在启动时投入，取消不触发效果，已投入材料不退还；没有产物空间时在完成处等待，期间不重复生效。

冷却运行期间若自然散热或另一条配方先降低了热量，完成仍结算，但最多降至零，不生成负热量；到零立即解除过热锁。维修同样最多恢复至配置容量。这保留源版的启动投入／完成结算，修正源版冷却减成负值和锁定无法恢复的边界，不对已投入的多余冷却材料退款。耐久保存为本机私有状态，重载或区块恢复不重新充满；损坏存档按零耐久处理。

CT 对应 `.addHyperNetCooling(20)` 和 `.addHyperNetCircuitRepair(100)`。脚本示例使用源版名称的独立预设线程：处理器 `novaeng.hypernet.data_processor.radiator`、中心 `novaeng.hypernet.maintenance_controller`。示例冷却耗雪球产黏土球、耗时 1 tick；维修耗铁锭产铁粒、耗时 100 tick，费用均由示例显式设置，非 MMC 默认配方。源版生成配方按核心 FE/t 的一半收费；本接口不猜测整合包的核心费用，需要作者按需填写。

两种需求不支持舱室 selector、延迟／重复触发或忽略输出检查；修改器对非负整数数量加／乘后向上取整，超出 int 范围拒绝。它们属于本地维护，不需要连接到中心才能冷却／维修，也不能修复远处其它机器。可视化编辑和 TOP 已接入；独立网络监控已接入，研究数据库后端、研究站与独立网络终端已接入，研究定义与配方门槛可视化已接入。

升级总线不作为配方原料／产物库存。冷却和维修应使用表中单独的输入／输出总线；模块仍通过升级总线安装。


## 可视化编辑与阶数提示（开发版）

用 `/modularmachinery gui` 选择已有机器，点“算力/说明”。等级说明页设置 T1／T2 等标签和最多 8 行说明，支持 `&a` 颜色代码和预览；等级只用于显示。网络、模块、散热和电路维修页修改对应参数。处理器模块映射点“模块等级与说明”可为该机器上的该模块另设提示；原物品及升级类型仍用既有注册方式声明。核心线程也仍须先用机器定义或 CT 建立，保存算力设置不会自动生成线程和配方。

例如在机器根节点或某条模块映射内加入：

```json
"display-info": {
  "tier": "&bT2",
  "tooltips": ["&6液冷数据处理器", "适用于本包的二级计算网络"]
}
```

独立控制器物品、机器蓝图和 TOP 显示机器提示；有相应升级映射的物品显示机器名、模块种类、容量、费用和模块提示。未设置 `display-info` 的旧机器无需修改。

配方输入点“+ → 资源／算力”，选择持续算力、主动冷却或电路维修。持续算力单位为算力/t，支持小数和短缺策略；冷却与维修数量为完工效果的整数。保存后可在批量设置中选是否随实际批量放大。不要为这三类需求设置接口分组、概率或输出方向。脚本生成配方在编辑器中仍只读。

TOP 的“上个 tick 实际算力”为成功提交值：中心是全网交付，处理器是自身供给，消费者是本机消耗，不能把三者相加。模拟和失败不计消费，查询本身不扣 FE、不散热或重连；中心可供给量是当时已发布额度，不保证后续供电。独立网络监控与持续需求登记已接入；可选公平调度已接入，研究站、数据库和独立网络终端现已接入。

## 网络监控（开发版）

打开启用了 HyperNet 的普通／工厂控制器，点击蓝图槽下方的“网”（英文 N）按钮。左侧选择已登记节点，左右箭头或在列表上滚轮翻页；右侧查看详情，“中心”“本机”切换查看对象，“返回”回到原控制器。每页六个节点，每秒更新一次，翻页请求可提前刷新。

实际算力取上个已完成世界 tick：中心为全网交付，处理器为自身交付，消费者为自身消耗。三者不能相加。配置承载／模块容量不等于当前可供给量；热量、电路耐久及停机原因用于排查缺模块、核心停机、未绑定等情况。长名称和省略的诊断可悬停查看。

“需求”取上个 tick 结束时仍待运行的配方，乘实际批量并应用修正器与批量豁免；悬停可看需求线程数。缺电或算力短缺而保留进度时仍有需求，已完成等待输出的配方为零，取消和停机也会清除。断网配方只保留本机需求，不计入中心；中心汇总有效连接消费节点，处理器自身没有消费需求。需求不会预扣资源，不保证预留或公平分配。例如两条各需 3 点的线程，供给 5 点时可显示需求 6、实耗 3。

列表仅是当前中心运行实例的暂存登记，最多 4096 项，不是持久离线历史。已知但未加载的节点显示不可用；查询不加载区块，定义重载或中心运行实例重建后重新登记。普通玩家须具备本控制器及网络所有权，OP2 可查看；窗口以原控制器为距离锚点，离开八格、控制器移除、机器改绑或定义重载后关闭。查看不扣 FE、不刷新散热、不发起算力请求，也没有库存槽。

底图来自 NECO 原终端，界面是本次移植的只读监控，不包含研究、数据库或源版终端收费。客户端与服务端均须使用协议 43 的同一开发版本，旧 JAR 尚不包含本功能。


## 中心公平分配（开发版）

在中心的 `hypernet` 对象中加 `"fair-scheduling": true`，或用 `/modularmachinery gui` 的“算力/说明 → 网络 → 公平调度”切换。默认关闭，沿用源版先请求先消费。只允许中心设置此布尔字段，处理器和消费节点不要添加。

例如中心已有承载与连接参数时：

```json
"hypernet": {
  "role": "center",
  "carrying": 1000,
  "max-connections": 16,
  "fair-scheduling": true
}
```

两条已启动的线程各需 3 点、实际供给 5 点时，会轮流工作；等待时保留进度，不因 `triggerFailure` 取消。缺电或其它材料时让出份额。每条线程的一次工作仍必须付全款，不能靠等待攒出超过整网供给的单次费用。公平模式下启动检查参考本 tick 的完整已公布供给，避免因前面的机器已扣费而一直无法启动；检查不入队或扣费，真正工作才轮换付款。直接 API 请求不参加排队；详细边界见适配文档。切换保存走既有重载流程，运行队列不跨重载保存。


### 短周期核心配方

中心与处理器的指定预设核心现在会在一轮完成后立即检查下一轮。材料和输出空间足够时，1 tick／2 tick 等短配方也可连续维持网络；下一轮只在下一 tick 推进，仍逐轮投入材料、逐工作 tick 扣 FE。缺料、输出堵塞或真实停机时不会保留虚假在线状态。无需增加宽限配置，也无需把核心配方人为延长到很大的时长。普通消费与维护线程沿用既有搜索策略。详细语义见适配说明的“核心配方的连续循环”。


## 研究门槛与数据库后端（开发中）

额外复制 `hn_sample_database.json` 到 `config/modularmachinery/machinery/`、`research/basic_materials.json` 到 `config/modularmachinery/research/`，以及 `research_backend.zs` 到 `scripts/`。这份脚本还依赖前面的 `hn_sample_node.json`。重载后可用同一中心的连接卡连接数据库，数据库工厂控制器须运行指定核心。

`storage-capacity` 是完成与进行中研究的条目总容量。配方使用 `.requireResearch("basic_materials")`；JSON 写法见适配说明。缺少研究会阻止投入材料，已启动配方不会因数据库中途离线取消。

**示例不会自动解锁研究**。研究站服务端已接入，玩家现在可安装独立网络终端操作任务，见末节。数据库核心已持续运行，输入 FE 按有效已完成成果数增长，进行中条目不加费。不要直接给玩家暴露进度写入 API。

### 研究站服务端示例

再复制 `hn_sample_research_station.json` 到 machinery 目录、`research_station.zs` 到 scripts 目录，连同上述数据库和研究定义使用。用工厂控制器成型、供电并连接同一中心；每个网络最多一台研究站，数据库和中心需真实运行。智能接口 `overclocking` 设置为 1..5，默认 1；每 tick 基础研究后，超频在 tick 结束消费普通配方剩余的算力。研究完成前短核心不会提前输出。

玩家任务通过独立终端提供，也可由可信服务端 Java 集成调用 `controller.getHyperNetNode().provideResearchTask("basic_materials", authenticatedPlayerUUID)` 提供，null 表示成功，非 null 为失败翻译键；这不是 ZenCode API。独立终端用法见末节。`cancelResearchTask` 保留数据库点数，下一次可恢复；任务不能换网继续成长。真实工作费用、持久化与未完成项见[适配说明](../../docs/NECO_GUIDE_ZH.md)。

### 数据库核心费用

示例基础为 1 FE/t；既有整数取整使小倍率不一定立即增加读数。可将 `research_backend.zs` 的基础输入改为 100 FE/t 来观察费用：0／1／3 项有效成果分别耗 100／110／130 FE/t。作者自己的能源修正器仍有效，不要另外实现同一份成果倍率。

指定数据库核心不会按 20 tick 周期完工；启动材料只在真正启动时投入，逐 tick FE 正常支付，完工输出不适合写在该核心中。其它维护线程仍正常运行。未绑定工作中心或无效账本会阻止核心启动／工作。未知成果保留并占槽，暂不计费，定义恢复后重新计费。独立终端现已提供，见末节。


## 独立网络终端

玩家现在可以通过独立的 **HyperNet 网络终端** 提供／取消研究。将本目录 `hypernet_terminal.json` 放入 `config/modularmachinery/machinery/`；它是只含能源舱与外壳的最小示例，作者可自行替换 `parts`。保留机器名 `hypernet_terminal`、`requires-blueprint: false`、`has-factory: false` 和角色 `terminal`，无需为终端编写配方线程。该结构并非新星工程整合包结构。

放置 `modularmachinery:hypernet_terminal_controller` 并完成结构、供电；在自己的计算中心用配置的卡片物品右键写卡，再将卡放入终端右下角槽中。每网限一台终端。未连中心消耗 200 FE/t，已连消耗 2,000 FE/t；单个输入舱必须能支付全额。断电后恢复供电，保留卡片，最多等待 20 tick 轮询重连。

终端沿用源版研究列表、说明区与玩家背包布局。搜索支持显示名或 ID，左键选择条目，滚轮／滚动条翻页，左键右侧开始图标启动，右键两次取消当前研究。取消保留数据库进度。研究站及工作数据库仍是必要设备，终端本身不生产算力、不免除研究费用。研究 JSON 的可选 `preview-item` 指定物品图标；示例使用铁锭。

当前协议 45，两端须使用相同开发版本。研究定义和数据库／研究站参数现可通过 GUI 编辑，见下节。此处示例仅供作者安装，不会自动写入现有整合包。


## 可视化配置研究

执行 `/modularmachinery gui`，选机器后打开“算力/说明”。“网络”页设置数据库成果容量或研究站科技上限；“研究”页查看全局研究目录，创建或修改参数，选择前置研究和物品图标，编写研究／解锁说明并预览颜色。物品搜索支持文字、ID、`@模组`、`#标签`。保存研究与保存机器参数分开进行。

已有研究 ID 固定，GUI 暂无研究删除；修改定义不授予成果、不清空数据库。外部改过文件须先重载并重新打开编辑器，以免覆盖他人修改。配方研究门槛可在输入框的 `+ → 研究门槛` 中搜索、勾选和保存；模板追加需求也可使用。支持最多 64 项且须全部满足，不消耗成果、不随批量放大。已有缺失 ID 会明确标红并保留到主动取消，不能新加未知 ID；研究目录失效时拒绝保存。脚本 `.requireResearch(...)` / JSON 写法继续可用。完整限制见[适配说明](../../docs/NECO_GUIDE_ZH.md)。


内置卡是移植新增的独立物品，未指定固定合成成本；整合包作者可编写获取配方。中心省略 `connection-card` 同样使用内置卡；旧配置若显式指定纸或其它物品则继续使用原物品。终端卡槽仅显示空槽／有效绑定／无效卡中的一种提示，分页信息位于列表滚动条悬停提示。


开发调试：创造模式且具有OP2级权限时，可在研究终端的开始按钮上按鼠标中键快速研究。它会填满当前任务点数，仍须满足前置、研究站等级、数据库和正常核心运行条件，不会直接解锁数据库，也不会覆盖正在进行的任务。普通玩家仍通过左键按实际算力研究。


### 带NBT的研究图标

普通图标继续写 `"preview-item": "minecraft:iron_ingot"`；带药水颜色、附魔、自定义模型或模组数据时，改用完整物品SNBT（不要同时填写preview-item）：

```json
{
  "id": "potion_preview_example",
  "display-name": "药水研究示例",
  "required-points": 100,
  "minimum-per-tick": 1,
  "preview-stack": "{id:'minecraft:potion',Count:1b,tag:{Potion:'minecraft:strong_healing',CustomPotionColor:3368703,CustomModelData:17}}"
}
```

预览数量始终为1，不表示研究成本或产物。图标SNBT上限16 KiB（UTF-8），嵌套最多64层；未知物品保留配置，显示时回退纸图标。终端和完成通知从服务端接收图标，不需要手动复制研究JSON到客户端，但两端必须使用兼容的MMC版本。

可视化编辑：打开机器编辑器 → 算力/说明 → 研究 → 选研究 → 图标，搜索后点击“背包”可从玩家库存复制图标，保留NBT且不消耗物品。点击“NBT”可查看和修改完整物品SNBT，点击“应用 NBT”后检查基本页预览，再保存研究。选择全部物品列表中的普通图标会替换原来的NBT图标。
